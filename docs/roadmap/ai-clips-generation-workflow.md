# AI Clips 第一阶段：三小时分析与动态批量选片

方案更新：2026-09-17；部署记录：2026-09-18。本文取代此前按视频时长规定候选数量的探索参数。实施状态与证据见 [验证记录](../video-workspace/ai-analysis-validation.md)。独立 Worker 已记录发布，应用开关随 GitHub 提交开启；三小时真实端到端能力仍未验收。

## 目标与范围

设置分析范围 → 后台发现与复审 → 查看候选 → 按需预览 → 单条编辑与导出。复用现有转写、词级时间戳、Cloudflare 媒体处理和编辑器，不重新转写。

- 每次分析最多 180 分钟。更长原视频必须明确选范围，不自动截断。
- 不改变上传、转写限制、套餐额度和导出额度。较短分析范围不代表转写费用下降。
- 默认 Auto 为 15–90 秒，也可选择 15–30、30–60、60–90 秒，均为单一连续区间；短源视频直编阈值仍为 45 秒。
- 不承诺每小时产出条数。零条是合法结果，不为达到数量补入广告、重复或不完整片段。
- 本阶段不包含批量 ZIP、跨项目模板、多段重组、成功后反复换主题或新的发布功能。
- 工程基线先在本地完成；生产发布记录见验证文档，付费远程压力测试与真实长素材内容评审仍待完成。

## 分批发现与预算

工程默认值集中于 [analysis-config.ts](../../lib/video-workspace/analysis-config.ts)，不是用户配额。

| 项目 | 默认预算 |
| --- | --- |
| 分析范围 | 最多 180 分钟 |
| 发现窗口 | 完整句子，目标不超过 10 分钟，同时最多 20,000 字符 |
| 相邻上下文 | 最多 90 秒，不突破选定范围 |
| 每批响应容量 | 0–12 条，不是产出目标 |
| 饱和批次补查 | 返回 12 条时二分补查一次，携带已发现范围 |
| 发现调用 | 最多 60 次，实际失败尝试也计入 |
| 待复审候选 | 最多 240 条 |
| 复审批次 | 最多 5 条 |
| 最多展示 | 120 条，超出时显示受限提示 |
| 全站／每用户并发 | 4／2；每项目最多一个活跃任务 |
| 每步尝试 | 每个重试周期最多 3 次；永久错误不自动重试 |

先完成所有原始批次，再补查。原始规划超过预算时不调用模型，要求缩小范围。处理中触及预算会保留受限状态，不声称已经充分发现全部内容。

初选先按时间重叠排除明显重复，再由模型按实际观点／故事分组供复审比较。主题相似不等于标题字符串相同。每组保留最强的合格版本，避免相同观点反复占位。模型分组发生在发现之后，不增加全片主题规划。

复审检查独立理解、问答完整、结尾、广告、用户条件和标题忠实度，沿用 accept / adjust / reject。调整后重新检查完整句子、词边界、15–90 秒和重复。最终范围确定后确认标题，不能靠标题补充缺失语境。按内容价值排序，同时保留不同观点。

## 后台与兼容

选片 worker 使用独立 Queue；D1 保存不可变输入、范围、转写标识／内容摘要、算法版本、步骤、尝试、租约与失败原因；R2 保存转写快照、批次输入、模型结果及报告。

- Queue 消息是唤醒提示，D1 才是任务状态来源。原子领取同时限制全站和每用户并发；租约 token 对过期写入作隔离。
- 每次外部尝试先记账。超时可能已经产生供应商费用，不声称模型调用严格只执行一次。
- 成功结果先写 R2，步骤写入失败可复用已有结果。成功批次保留，技术重试只恢复未完成步骤，不能修改范围或主题。
- 候选只在统一复审后提交。提交与项目状态更新同一事务，并检查任务租约，避免重投反复覆盖草稿或排序。手动候选不删除。
- Cron 恢复过期租约及漏发消息；等待转写的任务由后台检查现有转写状态并走既有完成／额度结算逻辑，不依赖浏览器触发。
- 已有候选不自动重分析；成功后的主题修改、权限及一次零匹配调整规则保留。

`POST /api/video-projects/:id/candidates` 接受可选 `analysisRange: {startMs,endMs}`。省略范围且全片不超过三小时则分析全片，返回 202 和现有候选／预览字段及任务状态。相同 requestId 返回同一任务；不同请求不能覆盖活跃或待技术重试任务。重试提交原 requestId 和 `retry:true`。

`GET` 增加阶段、实际已完成／总发现批次、选定范围、失败批次范围、受限原因和 canRetry；不制造百分比或 ETA。后台任务可以离开页面后继续。历史同步链路仅在开关关闭且没有已接收任务时保留。

## 媒体与界面

AI、编辑片段和最终时间轴都支持 90 秒；预览保留前后各 5 秒 handles。只自动预热前五条，其余首次打开时生成。结果默认采用左侧紧凑列表、右侧只读成片预览；可切换网格。可见卡片按实际构图、字幕和标题取静态帧后释放视频，完整播放器只保留当前选中项。编辑通过独立入口进入。生成前设置和验收见 [竞品流程落地](../video-workspace/clip-workflow.md)。

同一用户的排队任务中，主动打开预览、主动导出优先于自动预热，不抢占执行中任务；用户间仍按既有公平调度。高清仅处理明确导出请求。媒体实例规格和并发不变。

## 发布顺序与回滚（2026-09-18 已执行的顺序）

1. 先运行 `npx wrangler queues create scribix-ai-clips` 创建远程队列，再应用 D1 migrations `0042_ai_analysis_tasks.sql` 和 `0043_clip_review_mark.sql`。应用即使保持批量开关关闭，也依赖新增字段；仅推送应用代码不足以完成发布。
2. 发布支持 90 秒的媒体镜像和独立 `wrangler.ai-clips.jsonc` worker，配置现有 OpenAI／AssemblyAI 密钥。
3. 发布应用（Queue producer 和生成的环境类型已加入），保持 `AI_CLIPS_BATCH_ENABLED=false`。
4. 验证后开启服务端开关。

关闭开关阻止新链路接收新任务；已接收任务的 worker、Cron 和原 requestId 重试不检查开关，必须保留至任务完成。不能在有任务时删除新表或撤销 worker。任务 R2 前缀为 `ai-analysis/{userId}/{taskId}/`，纳入项目数据清理。

## 验收

工程覆盖范围边界、密集预算、重复提交、原子领取、临时错误／重投、存储故障、页面关闭、部分成功恢复、手动片段和草稿保护。媒体验证包含 60–90 秒编辑、预览、字幕、构图、MP4、封面及短片回归。

内容评审需要真实短素材、半小时、一小时、三小时，以及密集／稀疏场景。记录发现、拒绝、去重、最终数量与原因；人工独立完整且值得保留的条数、主题覆盖；候选、首条预览、人物分析、导出耗时；调用、资源消耗及可取得的实际成本。

2026-09-17 用户确认暂无合法长素材。合成文字稿只验证规划与资源上限，合成视频只验证媒体合同，不代替真实内容评审。三小时真实端到端验证完成前，不标记三小时能力已验收。

早期同素材竞品观察仅用于提出候选数量、时长和审阅流程问题；现行预算与时长以本文及代码合同为准，不能由竞品结果推断 Scribix 的产出条数或耗时承诺。
